# Budget-aware harness на openJiuwen

Харнесс решает набор задач за общий бюджет токенов и пишет `answer.txt` в каталог каждой задачи. Модель вызывается один раз на задачу и отвечает короткой программой, а исполняет и проверяет её харнесс.

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm \
  -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

| Переменная | Значение |
| --- | --- |
| `LLM_BASE_URL`, `LLM_API_KEY` | адрес и ключ прокси |
| `BUDGET` | бюджет в выходных токенах; без неё берётся 100 000 |
| `HARNESS_TRACE` | необязательно: путь к трассе вызовов, по умолчанию `/tmp/harness/trace.jsonl` |

Образ ничего не скачивает при запуске и пишет только в `/tmp` и в каталог задач. Базовый образ закреплён по digest, зависимости — полным lock-файлом `requirements.txt` (получен из `requirements.in` командой `uv pip compile`).

## Как это работает

1. `harness/tasks.py` читает `task.json` каждой задачи. Решатель выбирается по полю `task_type`; если тип неизвестен, он определяется по файлам в `workspace/`.
2. `harness/agent.py` сортирует задачи по убыванию `reward / ожидаемый расход` и решает их в 3 параллельные сессии.
3. Решатель строит короткий промпт, делает один вызов модели и проверяет ответ. Если проверка не прошла, следует один повтор на рассуждающей модели с текстом ошибки. Рискованные ответы затем перепроверяются (раздел «Второе мнение»).
4. Ответ пишется сразу после решения задачи в `answer.txt` рядом с `task.json`. Если у задачи есть `workspace/`, туда кладётся копия: инструкции говорят о «текущем каталоге». Если ответа нет, файл не создаётся.

Все вызовы LLM идут через `openjiuwen.core.foundation.llm.Model.invoke` (`harness/llm.py`). В запросе только системное сообщение, сообщение пользователя, `max_tokens` и `temperature=0`; схем инструментов нет.

### Решатели

| Семейство | Что видит модель | Что отвечает модель | Проверка харнесса |
| --- | --- | --- | --- |
| math | инструкция | выражение или несколько строк Python | программа выполнилась; для `exact_int` получилось целое |
| data_analysis | инструкция и схема таблиц: имена колонок, типы, диапазоны, значения категорий | выражение pandas над уже загруженным `DataFrame` | то же |
| search | инструкция и схема базы: группы карточек по набору полей, по одному примеру | выражение над словарём `kb['Заголовок']['Поле']` | то же; обращение к отсутствующей карточке или полю закрывает задачу |
| coding | исходник с номерами строк, тесты, вывод упавших тестов, строки, которые тесты не проверяют | вердикт по каждой функции и исправленные строки в виде `N\| код` | тесты задачи проходят в копии в `/tmp` |
| прочее | инструкция и листинг файлов с началом каждого | программа на Python | программа выполнилась, ответ не пуст |

Программа исполняется как ячейка REPL: значение последнего выражения становится ответом (`harness/runner.py`). Поэтому на простую задачу модель тратит 10–40 выходных токенов.

Карточки search читаются в форматах `Поле: значение`, `- Поле: значение`, `**Поле:** значение`. Если база написана прозой, модель получает текст заметок, которые относятся к вопросу, и отвечает по ним.

**Coding** идёт в три шага (`harness/solvers/coding.py`, `harness/solvers/mutate.py`):

1. **Замены операторов без модели.** Харнесс пробует обратные замены (`+=`/`-=`, `<`/`>`, `sorted`/`reversed`, `== 0`/`== 1`, `min`/`max`, `xs[:n]`/`xs[n:]`) и оставляет те, после которых упавшие тесты проходят.
2. **Строки, которые тесты не проверяют.** Харнесс ищет замены, после которых результат тестов не меняется. В таких строках баг может стоять за тестом, который проходит случайно. Модель получает обе версии каждой такой строки и выбирает по имени функции.
3. **Чтение моделью.** Модель видит исходник с номерами строк, по каждой функции пишет вердикт (`# имя: ok` или `# имя: bug`) и под вердиктом `bug` даёт исправленные строки. Вердикт по каждой функции не даёт ей ответить одним `OK` на весь файл. Правка принимается, если тесты стали проходить или упавших стало меньше; иначе она отбрасывается. Второй шаг получает текущее состояние с новой нумерацией. Если ответ оборван по `max_tokens`, его последняя строка не применяется.

Исправленные исходники копируются в `workspace/` только после прохода видимых тестов; иначе исходники остаются прежними и ответ не пишется. Слово для `answer.txt` берётся из инструкции (`the word DONE`). Файлы тестов харнесс не меняет.

### Второе мнение

Неверная программа тоже исполняется и печатает правдоподобное значение; проверки харнесса такого не видят. Один прогон тратит меньше десятой части бюджета, поэтому часть остатка идёт на перепроверку ответов, где модели ошибаются чаще всего (`risky` в `harness/solvers/pot.py`):

| Признак | Почему |
| --- | --- |
| math: программа не использует часть чисел из условия | так выглядит пропущенный шаг |
| search: программа считает агрегат (`min`, перебор карточек), а не идёт по цепочке `kb[...]` | в агрегатах модель путает ключ сравнения |
| search по заметкам в прозе | модель отвечает прямо, без программы над данными |

Перепроверка идёт после того, как все первые ответы записаны, в порядке убывания `reward`. Рассуждающая модель решает задачу заново. Если ответы совпали, ничего не меняется. Если разошлись, она получает обе программы с их результатами и выбирает; выбранный ответ записывается. На перепроверку уходит не больше половины бюджета. В примерах организаторов ни один ответ под эти признаки не попадает, и расход на них не растёт.

## Оценка расхода и бюджет

Расход считается по правилу: `выход + рассуждения + вход / 10`.

- **Учёт.** `Budget` в `harness/llm.py` ведёт счёт по `usage` каждого ответа. Перед вызовом резервируется верхняя оценка `вход / 10 + max_tokens`, поэтому параллельные вызовы не могут вместе выйти за бюджет. Неудачный вызов списывает оценку входа: прокси может засчитать и его.
- **Прогноз.** Вход известен до вызова, потому что промпт собирает харнесс. Выход ограничен параметром `max_tokens`, а не просьбой в промпте. Ожидаемый расход по семействам задан таблицей `EXPECTED_COST` в `harness/config.py`; она нужна только для порядка решения.
- **Запас.** 3% бюджета не тратится: счётчик прокси может расходиться с нашим.
- **Лимит прокси.** На ответ 429 харнесс снижает число параллельных вызовов на один и повторяет запрос; такой отказ токенов не стоит.
- **Остановка.** После трёх отказов прокси подряд харнесс перестаёт вызывать модель. Через 50 минут он перестаёт брать новые задачи. Уже записанные ответы остаются на диске.

Модели: первый вызов — `qwen3.8-27b-noreason`, повтор после провала проверки — `qwen3.8-27b` с жёстким `max_tokens=2000`. Рассуждения считаются как выходные токены, поэтому рассуждающая модель работает только как запасной шаг. Сравнение четырёх моделей делает `tools/compare_models.py`.

## Невыполнимые задачи

За невыполнимую задачу баллов нет при любом ответе, поэтому цель — не тратить на неё токены и не потерять при этом выполнимую.

Для невыполнимой задачи `answer.txt` не создаётся.

| Признак | Проверка | Вызовов модели |
| --- | --- | --- |
| У задачи нет входных файлов её типа: таблицы, карточек, кода с тестами | `missing_input` в `harness/tasks.py` | 0 |
| Два теста ждут разный результат от одного вызова, или файл тестов не разбирается как Python | разбор тестов в `harness/solvers/coding.py` | 0 |
| Программа обращается к карточке, полю или колонке, которых нет в данных и у которых нет похожих по написанию | текст `KeyError` после исполнения | 1 |
| Тесты coding не проходят после двух попыток | прогон тестов в копии | 2 |

- Решение о прекращении принимает харнесс, а не модель: не больше двух вызовов на задачу.
- Опечатка в имени (`unit` вместо `units`) невыполнимостью не считается и даёт повтор.
- Ошибка исполнения или ответ не того типа дают один повтор с текстом ошибки. Второй провал закрывает задачу.

## Замеры

Замеры сделаны на прокси `qwen` с цепочкой `qwen3.8-27b-noreason` → `qwen3.8-27b`. Расход указан в выходных токенах на задачу.

| Набор | Решено из выполнимых | Расход на задачу |
| --- | --- | --- |
| 8 примеров организаторов | 8/8 | 70 |
| 60 задач `tools/gen_tasks.py`: другие формулировки, грязные данные, невыполнимые | 47/47 | 69 |
| 120 задач повышенной сложности (math, data_analysis, search): лишние числа в условии, три перехода по базе, агрегаты, проза, соединение таблиц | 102/102 (без второго мнения 101/102) | 193 |
| 24 задачи coding, где баг стоит за проходящим тестом | 24/24 (без шага 2 и вердиктов было 20/24) | 111 |

Сравнение моделей на тех же 60 задачах, каждая модель одна, без цепочки (`tools/compare_models.py`):

| Модель | Решено из 47 | Расход на задачу | Секунд на вызов |
| --- | --- | --- | --- |
| `qwen3.6-35b-a3b-noreason` | 43 | 63 | 4.4 |
| `qwen3.8-27b-noreason` | 46 | 63 | 3.8 |
| `qwen3.6-35b-a3b` | 38 | 593 | 9.0 |
| `qwen3.8-27b` | 47 | 226 | 7.5 |

Каждая модель прогонялась один раз, поэтому разница в 1–3 задачи лежит в пределах шума. Тренировочные задачи сгенерированы нами и не совпадают с финальным набором.

## Траектории

Каждый вызов модели пишется строкой JSON: задача и номер шага, модель, сообщения, ответ, токены входа и выхода, стоимость, накопленный расход. По этим трассам подобраны цепочка моделей и таблица `EXPECTED_COST`.

| Файл | Что в нём |
| --- | --- |
| `traces/examples.jsonl` | 8 примеров организаторов, 8 вызовов |
| `traces/train60.jsonl` | 60 тренировочных задач, 56 вызовов |
| `traces/train60.report.txt` | итог того же прогона по задачам: решена ли, число вызовов, расход |

## Локальная проверка

```bash
uv venv --python 3.12 .venv && uv pip install -p .venv/bin/python -r requirements.txt pytest
.venv/bin/python -m pytest tests
.venv/bin/python tools/stub_llm.py --port 8089 &
LLM_BASE_URL=http://127.0.0.1:8089/v1 LLM_API_KEY=x \
  .venv/bin/python tools/eval.py examples/tasks --budget 5000
```

`tools/eval.py` копирует набор задач, запускает харнесс и сверяет ответы с полем `expected`. Харнесс поле `expected` не читает. `tools/gen_tasks.py` генерирует тренировочные задачи четырёх типов, `tools/compare_models.py` прогоняет один набор на каждой из четырёх моделей.
